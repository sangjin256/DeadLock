# DeadLock 게임 디자인

## 문서 목적

이 문서는 DeadLock 퍼즐 게임 부활과 모바일 이식 작업의 로컬 디자인 기준이다.

## 현재 핵심

- 플레이어는 프로세스의 색상 슬롯을 호환되는 리소스 노드에 연결한다.
- 플레이어가 필요한 연결을 모두 예약한 뒤 라운드 단위 시뮬레이션이 실행된다.
- 리소스는 수용량, 색상, 동시 연결, 색상 전환, 빈 색상, 시계 제약을 가질 수 있다.
- 성공 조건은 레벨 규칙 안에서 모든 프로세스 노드가 완료되는 것이다.

## 색상 판정과 실제 표현

도메인에서 색상은 실제 화면 색상 코드가 아니라 `ColorId`로 표현되는 규칙 판정용 ID다. 프로세스 슬롯과 리소스가 같은 색인지, ColorSwitch의 현재 색과 슬롯 색이 맞는지, Relay Transfer가 전달한 색이 Receiver에 맞는지는 `ColorId` 비교로 판단한다.

실제 화면 색상, 아이콘, 머티리얼, 색약 보정 팔레트는 Domain 밖의 ScriptableObject, VisualSettings, View 계층에서 `ColorId`에 매핑한다. 따라서 같은 레벨 규칙을 유지한 채 기본 팔레트, 접근성 팔레트, 이벤트 스킨 같은 표현만 바꿀 수 있다.

## 레거시 핵심 플레이 규칙

레거시 런타임 기준으로 플레이는 시작 전 계획 단계와 라운드 시뮬레이션 단계가 분리된다.

- 플레이어는 시작 전에 모든 프로세스 색상 슬롯을 리소스에 예약해야 한다.
- 시작 전 연결 가능 여부는 "그 리소스가 해당 색을 언젠가 처리할 수 있는가"로 판단한다.
- 시작 전 예약은 리소스 capacity를 소모하지 않는다.
- 시뮬레이션 중 실제 연결 가능 여부는 프로세스 상태, 현재 리소스 색/상태, 남은 capacity, 리소스 Rule 조건으로 판단한다.
- 리소스 슬롯은 개별 색 작업이 끝났다고 바로 반환되지 않는다. 해당 슬롯을 점유한 프로세스의 모든 작업이 완료될 때 반환된다.
- 다른 프로세스가 이미 점유된 리소스에 접근하면 그 리소스의 대기열에 들어가고 waiting 상태가 된다.
- waiting은 재선택 상태가 아니다. waiting 중인 프로세스는 다른 리소스로 진행하지 않고, 대기 중인 리소스 앞에서 기다린다.
- 리소스 슬롯이 풀리면 대기열의 맨 앞 항목만 다음 라운드 맨 앞으로 재투입된다. 맨 앞 항목이 실패해도 뒤 항목이 먼저 재투입되지 않는 strict FIFO를 유지한다.
- 모든 프로세스가 완료되면 성공한다.
- 모든 미완료 프로세스가 waiting이고 풀릴 가능성이 없으면 deadlock 실패다.
- fixed finish order가 있는 프로세스는 지정된 완료 순서를 어기면 실패한다.
- Clock 리소스가 닫히는 시점에 미완료 프로세스가 해당 리소스를 점유 중이면 실패한다.

## 리소스 규칙

리소스는 단일 타입보다 capacity와 내부 Rule 조합으로 본다.

- Basic: 현재 리소스 색과 프로세스 슬롯 색이 같고 capacity가 남아 있으면 시뮬레이션 중 연결된다.
- Capacity: 한 리소스가 동시에 점유할 수 있는 슬롯 수다. 시작 전 예약 수가 아니라 시뮬레이션 중 실제 점유 수를 제한한다.
- Simultaneous: 연결 가능 여부보다 완료 가능 여부를 보류하는 규칙이다. 필요한 수는 해당 리소스의 capacity와 같고, capacity만큼 점유되기 전까지 해당 리소스를 점유한 프로세스는 완료되지 않는다.
- ColorSwitch: 시작 전에는 색 목록에 포함된 색이면 예약 가능하다. 시뮬레이션 중에는 현재 색과 맞아야 연결된다. 프로세스가 리소스를 반환할 때 색이 다음 색으로 순환한다. 리소스가 비어 있고 해당 라운드에 아무도 점유하지 못했을 때도 라운드 종료 시 다음 색으로 순환한다. waiting queue는 색이 맞는 항목을 검색하지 않고 strict FIFO를 유지한다.
- EmptyColor: 처음에는 어떤 색이든 받을 수 있고, 첫 실제 연결 색으로 리소스 색이 고정된다. 이후에는 고정된 색과 맞아야 한다. 시뮬레이션 리셋 시 고정 상태는 해제된다.
- Clock: 카운트는 실시간이 아니라 라운드 종료마다 감소한다. OnToOff는 처음 열려 있다가 닫히고, OffToOn은 처음 닫혀 있다가 열린다. OnToOff가 닫히는 순간 미완료 프로세스가 해당 리소스를 점유 중이면 실패한다.

## 새로 추가할 퍼즐: Relay

Relay는 새 리소스 종류가 아니라, 기존 리소스 위에 추가로 얹히는 공간 퍼즐 모디파이어다. Basic, Capacity, Simultaneous, ColorSwitch, EmptyColor, Clock 같은 리소스가 먼저 있고, 그 리소스 두 개가 Relay 관계로 묶일 수 있다.

Relay의 목적은 보드 위에서 멀리 떨어진 리소스들이 서로 영향을 주게 만들어, 단순히 가까운 리소스에 선을 연결하는 문제를 넘어 공간적 판단을 요구하는 것이다. 색을 새 규칙으로 더 많이 추가하면 플레이어가 헷갈릴 수 있으므로, Relay는 색보다 라인, 끝 장식, 상태 변화, 모션으로 구분한다.

공통 규칙:

- Relay는 항상 두 리소스를 한 쌍으로 묶는다.
- Relay 관계는 프로세스의 필요 색과 별개의 규칙이다.
- Relay가 붙어도 각 리소스의 기존 규칙은 유지된다.
- 기본 상태에서는 두 리소스가 Relay로 묶여 있다는 힌트만 보여주고, 리소스 선택 또는 hover/tap 시 전체 연결선을 보여준다.
- 모바일에서는 hover가 없으므로, Relay가 붙은 리소스를 탭했을 때 연결된 상대 리소스와 전체 Relay 라인이 잠시 강조된다.

### Relay Link

Relay Link는 연결된 두 리소스가 서로 같은 상태 그룹에 묶이는 퍼즐이다.

기본 아이디어는 "한쪽을 사용하고 있으면 다른쪽도 영향을 받는다"이다. 예를 들어 한쪽 리소스가 이번 라운드에 사용 중이면, Link로 묶인 다른 리소스도 잠김 상태가 되거나 같은 사용 상태로 표시될 수 있다. 이 규칙은 플레이어가 리소스를 각각 독립된 노드로만 보지 않고, 떨어진 두 리소스를 하나의 세트로 보게 만든다.

초기 구현 규칙:

- 예약 단계에서는 양쪽 리소스에 모두 연결을 예약할 수 있다.
- 시뮬레이션 중 한쪽 리소스가 실제 점유되면, 그 프로세스가 완료되어 리소스를 반환할 때까지 반대쪽 리소스는 사용할 수 없다.
- 반대쪽 리소스에 접근한 프로세스는 일반 capacity 초과와 같은 방식으로 waiting queue에 들어간다.
- 한쪽 점유가 끝나면 반대쪽 잠금이 해제되고 waiting 항목은 다음 라운드 우선 항목으로 재투입될 수 있다.

### Relay Transfer

Relay Transfer는 한쪽 리소스의 입력 색이 다른쪽 리소스로 전달되는 방향성 퍼즐이다.

기본 아이디어는 "A에 연결한 색이 B의 임시 색을 만든다"이다. Link가 두 리소스를 같은 묶음으로 보는 규칙이라면, Transfer는 송신 리소스와 수신 리소스가 분명한 전달 규칙이다. 따라서 Transfer는 Link보다 방향 표시가 중요하다.

초기 구현 규칙:

- Relay Transfer는 방향성 `Sender -> Receiver` 관계다.
- Sender 리소스를 실제 점유한 슬롯의 색이 Receiver 리소스의 임시 색이 된다.
- Sender 리소스의 capacity는 1만 허용한다. 이는 인게임 Rule 방어가 아니라 레벨 에디터/ScriptableObject authoring 단계의 검증 제약으로 둔다.
- Receiver는 시작 전 예약 단계에서 아직 전달 색이 없더라도 예약할 수 있다. 실제 연결 성공 여부는 시뮬레이션 중 Sender가 전달한 현재 색으로 판정한다.
- Sender 점유가 끝나고 리소스가 반환되면 Receiver의 전달 색은 사라진다.
- Receiver가 이미 점유 중이면 현재 작업이 끝날 때까지 기존 색을 유지한다. 새 전달 색이나 전달 색 해제는 Receiver 반환 뒤에 적용한다.
- 이 규칙은 Receiver를 단순히 unlock하는 규칙이 아니다. 색 전달 자체가 Transfer의 핵심이다.

### Relay를 리소스 타입으로 만들지 않는 이유

Relay는 리소스 하나의 성질이 아니라 두 리소스 사이의 관계다. 그래서 `RelayResource`처럼 독립 리소스로 만들기보다, 레벨 데이터에서 두 리소스 사이에 `RelayLink` 또는 `RelayTransfer` 관계를 추가하는 방식이 적합하다.

이렇게 하면 같은 Basic 리소스라도 어떤 레벨에서는 일반 Basic이고, 다른 레벨에서는 Relay Link가 붙은 Basic이 될 수 있다. 기존 퍼즐 규칙을 버리지 않고 조합을 늘릴 수 있다는 장점이 있다.

### 레벨 디자인 활용

Relay Link는 "둘 중 하나만 쓸 수 있는 선택"을 만드는 챕터에 적합하다. 플레이어는 단순히 색이 맞는 리소스를 찾는 것이 아니라, 그 리소스를 쓰면 멀리 있는 다른 리소스가 막히는지까지 고려해야 한다.

Relay Transfer는 "먼 곳의 리소스 색을 간접적으로 만드는 흐름"을 만드는 챕터에 적합하다. 직접 원하는 색으로 연결하기 어려운 리소스를 다른 리소스의 입력 색으로 물들이거나, 특정 순서로 색을 전달해야 하는 퍼즐에 사용할 수 있다.

두 규칙은 같은 챕터에 바로 섞기보다, 각각 별도의 퍼즐 챕터로 소개하는 것을 우선한다. Link는 공유/잠금의 개념을 먼저 학습시키고, Transfer는 방향성과 전달 개념을 별도로 학습시킨다.

## 디자인 우선순위

1. 원작 퍼즐의 가독성과 논리를 보존한다.
2. 모바일 조작성을 개선한다.
3. 게임 상태를 흐리지 않는 범위에서 비주얼 피드백을 강화한다.
4. 퍼즐 규칙은 Unity 밖에서도 테스트 가능하게 만든다.

## 레벨 에디터 방향

레벨 하나는 `LevelSO` 하나로 저장한다. `LevelSO` 안에는 보드 크기, process, process slot, resource, relay, test case 데이터가 함께 들어가며, 내부 데이터 타입은 별도 ScriptableObject가 아니라 직렬화 데이터로 둔다.

레벨 에디터는 UI Toolkit 기반 전용 창으로 만든다. 목표 UX는 인스펙터에서 칸마다 버튼을 누르는 방식이 아니라, grid canvas에 process/resource를 배치하고, relay link/transfer를 시각적으로 연결하며, 선택 항목 inspector에서 세부 값을 편집하는 방식이다.

에디터는 제작 중 검증과 테스트를 우선 기능으로 가진다. `LevelSO`를 Domain `LevelDefinition`으로 변환한 뒤 `LevelDefinitionValidator` 결과를 에러 리스트로 보여주고, 에러를 선택하면 관련 노드나 relay를 강조하는 흐름을 목표로 한다.

자동 플레이 검증은 test case 기반으로 시작한다. `LevelSO`에 저장된 test case는 process slot과 resource의 예약 연결 목록, 예상 결과, 최대 라운드 수를 가진다. 에디터는 이를 자동으로 `Board.AssignConnection()`에 적용하고 `Board.RunSimulation()`을 실행해 round-by-round 결과를 재생한다. 이후 클리어 라운드 수, waiting 횟수, relay 사용 여부, clock 여유 라운드 같은 지표로 난이도 분석을 확장한다.

## 열린 디자인 메모

- 현재 원/사각형 노드 비주얼은 변경될 수 있다.
- 연결은 물방울, 젤, 표면장력 시각 언어를 탐색한다.
- 정적 레벨 ScriptableObject는 유지할 수 있지만, 런타임 규칙은 순수 Domain 객체로 이동하는 것을 목표로 한다.
- ScriptableObject 레벨 데이터는 Domain의 `LevelDefinition`으로 변환하고, `LevelDefinitionValidator`로 authoring 오류를 검증한 뒤 `LevelBoardFactory`가 런타임 `Board`를 생성한다.
